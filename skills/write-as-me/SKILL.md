# write-as-me

Drafts must read like Kevin wrote them, not like AI output. Before the first draft in a session, read:

- `references/style-guide.md`: voice, registers, investigation shape, phrases, avoid list
- `references/examples.md`: paraphrased examples per situation and register

## Hard rules

- No profanity or crude wording, in any register.
- Never frame findings as AI output ("Claude / AI / Codex found...", "Generated by..."). State findings as his own.
- No em dashes, headers, bold, or tables in the draft. Code and logs go in ``` blocks.
- One sentence per line: after every sentence-ending `.`, `?` or `!`, start a new line. This doesn't apply inside URLs, numbers (`1.5`, `v2.3`), abbreviations (e.g., i.e., etc.), ellipses (`...`), file names, or code. In a bullet, a second sentence becomes its own bullet.
- No secrets, tokens, or credentials. No customer personal data beyond what the thread already has and the reply needs.
- Never post without an explicit OK from the user in this conversation.

## Workflow

1. **Read the context.** If there is a thread or channel link, read it: who is asking, what has been said, what is being asked of Kevin. For investigation write-ups, use the findings from this session.
2. **Classify the audience.**
   - Internal casual: his own team, teammate DMs, his manager.
   - Internal cross-team: other teams, support, on-call, incident channels.
   - External: customers, vendors, partners, shared cross-company channels, or anything the reader will relay to a customer verbatim.
3. **Pick the register.** Default is **slightly formal** for every internal audience. Use **formal** for external. Use casual only when the user asks for it.
4. **Write the draft** using the style guide. Investigation and incident write-ups follow the "Investigation / incident write-ups" shape.
5. **Self-check** before saving it:
   - Register matches the table in the style guide.
   - As short as the content allows. No intro restating the question, no closing pleasantries he doesn't use.
   - At most one hedge ("I think" / "seems") and at most one emoji (none when formal).
   - Investigation / incident write-ups: a conclusion line plus 2-4 bullets, 3-6 lines in total, simple colloquial words, no exception / class / method names.
   - Nothing from the Avoid list. Hard rules hold.
6. **Output: always a Slack draft, never the text in chat.**
   - Save the draft with the Slack connector's draft tool (e.g. `slack_send_message_draft`, passing `thread_ts` for thread replies) so Kevin only has to review and press send.
   - Do not paste the draft text into the chat reply. Reply with one line naming the target, the register, and the channel link, plus any caveat he needs before sending (e.g. a fact that couldn't be verified).
   - Never use the send tool for these drafts.
   - One draft per target. Slack keeps one draft per channel or thread and silently ignores another save there: a save that returns a `draft_id` created the draft, and one that returns no `draft_id` saved nothing. Never report a save without a `draft_id` as done.
   - Redrafting: ask Kevin to delete the current draft in that channel or thread first, wait for his OK, then save the new version and confirm the response has a `draft_id`. Never put versions in other channels, DMs or threads.
   - No target yet: ask for the thread or channel link. Don't write the draft in chat instead.
   - No `draft_id` or `draft_already_exists`: nothing was saved. Tell him to delete the existing draft there, then retry. Show the text in chat only if he asks.
   - Non-Slack targets (tickets, docs): show the draft in chat for him to paste.

## Feedback loop

When Kevin edits a draft, rejects a phrase, or says he wouldn't write it that way, update `references/style-guide.md` (adjust a rule or add to Avoid) or add the corrected message to `references/examples.md`, and tell him what changed.

- Edit the source in the skills repository (https://github.com/fsw0422/skills), preferably in its active worktree rather than through an installed skill symlink.
- Commit on a branch and open or update a PR for him to merge; never push to `main`. After the merge, update `~/skills` from `main`. Claude and Codex read the linked files directly, so no plugin update is needed.
- The repository is public. Keep both files free of workplace-specific names (company, teams, channels, internal services), Slack IDs, people's names, customer details, and secrets. Paraphrase new examples with placeholders.
