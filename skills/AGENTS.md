# General

For any final output generated by you:
- Use concise, easy wording and plenty of examples.
- Maximize utilization of Mermaid Diagram for visualization (flow chart, sequence diagram especially). However for flowcharts, please use it only if there are branches. Simple steps can just be explained in numbering.
  - Draw and check every diagram, in chat or in files such as specs, with the `mermaid-image` skill.
- When you explain a change, show its key changed lines, not only a link: code as a small `diff` block with short notes, prose as a quote of the new wording. A link opens the whole current file, not the change.

# Code

- Write simple, concise, human-readable code.
- Don't write huge class files or very long methods. Split them along clear responsibilities.
- Before writing generic functionality, such as a hashing function, check for an existing library first.

# Browser

- Before using any browser tool, load and follow the `browser-pilot` skill, even when no other skill asked for it.
- Never drive the user's own Chrome: no Claude in Chrome, no Codex Chrome plugin, and no other extension-based browser tool.

# GitHub tool routing

- Use the `gh` CLI first for GitHub repositories, pull requests, issues, reviews, comments, checks, workflows, and API reads. Treat a GitHub URL as a resource identifier, not a request to open a browser. Prefer `--json` and `--jq`, and use `gh api` when a first-class command lacks a field.
- If `gh` fails because sandbox networking is blocked, retry the same minimal command with network escalation or approval before diagnosing authentication or changing tools. Do not treat an in-sandbox connectivity failure as an invalid token.
- Do not switch silently to Browser or Chrome. Use browser automation for GitHub only when the user explicitly requests it, the task genuinely requires browser-only UI interaction, or `gh` still cannot perform the task after connectivity and authentication are verified. Explain why and obtain explicit approval before falling back.
- CLI-first routing does not authorize GitHub writes. Preserve the user's requested scope and all workflow-specific confirmation requirements.
- Browser and Chrome remain appropriate for local visual and UI testing; these GitHub rules do not change that.

# Pull requests

- Right after creating a pull request, draft or ready for review, open it in a new browser tab, following the `browser-pilot` skill, so the user can review it.
- After pushing code for any PR in progress, update its description. Remove information that is no longer relevant and add or revise details to match the latest changes.
